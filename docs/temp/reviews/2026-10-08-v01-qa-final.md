## Findings

**QA-V01-01 — P2: abandoned Command Code lookup can dispatch a late usage request.** In the initially reviewed source, `lib/providers/commandCode.js:29` awaits `getKey()` and `:40` invokes HTTP without checking the scheduler context again. `lib/services/http.js` creates a one-second context watcher only after preparing a request; it calls `session.send_async()` before the watcher checks cancellation. Its original `dispose()` also has no persistent closed state. A lookup held while credentials change, the scheduler times out or the provider is disposed can therefore start an obsolete request afterward. The output fence prevents obsolete snapshots, but does not prevent this request. The same-epoch credential-change case is particularly relevant because the provider's gate ticket can remain valid while the scheduler revision has cancelled its context.

Executed reproduction imports the actual `createCommandCodeProvider`, holds its injected key promise, cancels its context, then releases the printable synthetic key. Its injected HTTP adapter records `{"requests":[{"cancelled":true}]}`; GJS exits 0. This proves dispatch into the HTTP boundary, not a real-provider request or disclosure. Root independently confirmed the source path and assigned `v01_http_cancel_fix` ownership of Command Code, HTTP and affected tests. Required disposition: post-await provider check, client cancellation/closed admission checks and meaningful request-count assertions, while retaining accepted OAuth rotation persistence through its separate refresh client. Correction is independently approved after source freeze. Command Code checks disposal and context immediately after key lookup; HTTP rejects disposed clients and cancelled contexts before request preparation/send, with no intervening await. Existing in-flight deadline/watcher cancellation remains. Independent focused results: Command Code **5/0**, HTTP **10/0**, provider config **19/0**, each exit 0 in private five-XDG environments. Actual loopback healthy requests succeed; cancelled GET and disposed POST add zero server arrivals. The accepted-rotation regression still stores the new refresh token after provider disposal and starts no usage HTTP. No change closes the separate refresh client during ordinary provider disposal. Root full/package reruns remain necessary.

No additional confirmed P0/P1 was identified within the reviewed scope. Root-supplied effects and preferences logs contain allocation/viewport warnings during scripted transitions; passing assertions must not be described as a zero-warning run. They are not independently established new regressions in this review.
