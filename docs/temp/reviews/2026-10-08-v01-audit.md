### Pending source findings

- **P2, credential-change integration ordering**: the `changed::credentials-revision` handler in `extension.js` awaits `_syncProviders()` before calling `controller.credentialsChanged(touched)`. `_syncProviders()` awaits every candidate's keyring lookup; `isConnected()` can wait ten seconds. A same-epoch login/delete does not independently advance the gate epoch or cancel the scheduler context. An old request may therefore publish during the lookup delay, before the scheduler's revision fence activates. The independent security reviewer executed an entirely synthetic reproduction with the actual extracted extension callback and real `PollScheduler`: while sync was held, context cancellation remained false and an old successful 91% snapshot or old `auth_required` failure published. This confirms the P2; correction ownership and independent rereview remain pending. Reviewer's focused injected token/disconnect/OAuth-controller suites passed 30 + 34 + 39 assertions; those existing suites miss the extension callback ordering.
- **P2, user System-theme override presentation**: UX reviewer reports `prefs.js:121`–`:128` groups and labels any default-theme ID as “System (GNOME)” regardless of loader-owned user provenance; `prefs.js:211`–`:214` similarly selects the official display name. A valid user override named `sistema-gnome` therefore receives the built-in label/description while native effects correctly remain disabled. This contradicts the documented identification of overrides as user themes. Source-only reproduction: install a valid synthetic user override with that ID and a custom name/color, then inspect the picker/general display. No real theme directory or native session was used. Awaiting full independent review/disposition.
- **Architecture observation, synchronous Shell configuration I/O**: `lib/providers/index.js:92`–`:94` calls synchronous `readLocalConfig()` in Shell refresh/Antigravity User-Agent handling. `lib/services/localConfig.js:24` and `:47` perform synchronous file queries and `load_contents`, despite the available asynchronous reader. TTL caching limits frequency, not the latency of an individual read; pre-stat size does not itself bound a concurrently replaced file's contents. This is a source observation against the async-I/O principle, not an executed freeze/attack demonstration or a new secret exposure claim. Root must decide its release disposition.
- **P2, jitter breaks retry bounds**: `lib/core/scheduler.js` applies `_jittered(delay)` after `_backoffMs()` and Retry-After clamping. With a capped one-hour delay and maximum positive jitter, the result is 66 minutes, exceeding the documented one-hour hard cap in ADR 0002. With an accepted ten-minute Retry-After and minimum random value, the result is nine minutes, earlier than the server's requested delay. Both are direct arithmetic/source traces, not coordinator-executed tests. Current scheduler cap tests inject random 0.5 and cover zero jitter only. Root should assign endpoint jitter regressions and preserve the server lower bound within the accepted upper cap.
- **P2, setup threshold bypasses pair validation**: UX reviewer reports `lib/prefs/firstUse.js:163`–`:166` writes a shared critical threshold to all quota types without checking enabled warnings. Starting from warning enabled at 80% and critical 95%, rerunning setup and choosing critical 70% writes an invalid pair. The advanced Notifications view rejects the equivalent change, while `AlertService` preserves the previous effective 95% pair through its valid-rule backup. Setup can therefore show 70% while runtime retains 95%. This is a source-only interleaving reviewed by coordinator; native reproduction and correction disposition remain root-owned. Ensure validation/feedback or an explicitly accepted atomic pair policy rather than silently misrepresenting the effective threshold.
