# Accounts and multiple connectors: design and implementation contract

Date: 2026-10-08. Status: design handoff for the user-authorized Accounts redesign. This document describes intended behavior; it does not claim implementation or validation has finished.

## Purpose and evidence

The user needs to create and remove connectors for the supported providers, including two independent accounts for one provider, and recover default settings without being unable to configure a connector. Each connector must produce its own quota card and status. Quotas from different accounts must never be added together.

Read-only investigation found that the current Accounts page loops over `availableProviders()` and keys its controller map by `meta.id`. This singleton identity continues through keyring attributes, provider factories, scheduler snapshots, cache records, status, paused-provider settings, popup targets and notification lookup. Adding another Accounts row alone would overwrite or share the first account. The redesign therefore includes an identity contract, not only a different layout.

The current Restore action intentionally resets only `RESET_KEYS`. It preserves accounts, paused-provider choices, first-use dismissal and the data source. That explains some expectations differing from current behavior, but does not prove that the batch reset itself is broken. A native test must first change representative settings and inspect their values before and after confirmation. The screenshot showing invalid JSON is consistent with a copied empty `/dev/null` configuration: this is not a usable OAuth client configuration. The current demo Accounts page still constructs production controllers and can display missing-client/keyring conditions; synthetic connector testing must instead use explicitly simulated controllers.

## Chosen interaction

Keep the existing native GTK/libadwaita Preferences window and Accounts tab. Use a single primary **Add connector…** button followed by provider groups containing only their existing connectors. Each connector row displays a user label and trusted provider name, followed by a concise state such as Connected, Not connected, Paused or Needs attention. A trailing edit button opens the connector editor. A switch controls tracking independently for this connector. Do not expose the immutable identifier as user-facing content.

**Add connector** opens a native dialog with an `Adw.ComboRow` listing Command Code, Codex, Claude and Antigravity, and an `Adw.EntryRow` for the label. Default labels distinguish subsequent accounts, for example “Codex 2”. Creating metadata does not start sign-in. After creation, open the editor and focus its first available configuration action. For an API-key connector, show its account username, keys-page link, password field and Apply action. For OAuth, show connection status, Connect/Reconnect/Cancel, the current missing-client configuration instruction, the helper command and a visible **Check configuration again** action. Configuration belongs to the provider client, while the credential belongs to this connector.

The editor supports renaming, tracking, connecting/reconnecting and **Remove connector…**. Removing presents a confirmation naming the provider and local connector label; Cancel is the default and close response. Removal deletes only this connector's local credential and quota/alert state, then its metadata after absence is confirmed. Provider sessions and API keys can remain valid on their sites. On partial failure, retain the connector row, show a fixed failure message and offer Retry; never show success or silently orphan a secret. When removal succeeds, focus the following connector, previous connector or Add button.

Keep the existing shared connection controller between Accounts and the first-use assistant. The controller registry is keyed by connector ID. The assistant may select providers and reuse/create their default connector without creating a new account on every reopening. Popup “Add account” always opens Add connector, even if every supported provider already has an account. Popup manage-account actions target the exact connector.

## UI, UX and frontend agreement

The preferred layout is a compact connector list plus a focused editor. It keeps a second account discoverable and reduces repeated key and OAuth controls. Expanding every account inline remains feasible but makes scanning and keyboard navigation worse as accounts grow. A separate page per provider adds unnecessary navigation and makes “another account for this provider” harder to find. The selected list/editor design follows existing native preferences conventions and reuses controller-backed account groups.

Use native semantic text and button styles rather than popup-theme CSS in GTK. Group titles communicate provider identity, labels communicate the user's account distinction, and state text communicates operational condition. Use 8-unit spacing where custom container spacing is required. Controls retain GTK focus indication; loading, disabled and failure states use text in addition to color. Actions wrap at narrow widths and translated text must not overlap suffixes. Password fields remain masked and clear when saved or closed. No ambient motion is needed for account editing.

Every icon-only action has an accessible name including the trusted provider and sanitized connector label. Tab order follows list, Add, editor inputs and editor actions; Escape closes the editor or cancels the current confirmation. Busy sign-in focuses Cancel, and the end of sign-in returns focus to the next available primary action. Deleting a focused row must move focus predictably. State announcements must be checked using actual GTK accessibility support; a harness that disables accessibility is not evidence of Orca behavior.

## Stable identity and migration

Define a pure connector module with validated records `{id, providerId, label, username}` and a versioned serialized collection. `providerId` must be a supported registry ID. Keep existing singleton default IDs equal to provider IDs (`codex`, `claude`, `command-code`, `antigravity`). Generate added IDs as `providerId--UUID`; these remain under the current 64-character snapshot-ID limit. IDs never change after rename and are never reused after deletion.

Store connector metadata in a new schema setting such as `connectors`, a string containing `{version: 1, connectors: [...]}`. An unset/empty initial setting is the sole migration trigger. Serialize the initialized collection even when it is empty, so removing all accounts cannot recreate defaults on restart. Bound input size, cap the list at the existing cache limit of 32 accounts, reject duplicate IDs and unsupported providers, and sanitize bounded labels/usernames. Labels are optional local display text, never secrets or provider-authenticated account identities. Read the migration's existing paused-provider and Command Code username settings; migrate those references to the corresponding default connector. Preserve existing default IDs, cache keys and credential locations. No secret read, copy or deletion is required for the identity migration.

Legacy default connectors continue using the existing libsecret schema and exact `{provider, kind}` identity. Added connectors use a **separate schema namespace**, with exact `{provider, connector, kind}` attributes. Adding `connector` to the old namespace is unsafe: an old lookup or deletion with only `{provider, kind}` would also match new accounts, and noninteractive lookup currently takes the first matching item. The namespace split prevents arbitrary first-item selection and cross-account deletion. New read, store, erase and presence operations require an explicit validated connector identity.

The coordination gate can remain provider-wide for conservative exclusion: its existing fixed provider allowlist is retained. A credential operation specifies both its connector identity for secret addressing and its `providerId` for the lease/ticket. Never pass a new connector ID into the current gate's fixed provider allowlist. Two accounts may fetch usage independently while mutations serialize per provider. Conditional OAuth replacement still compares the exact connector's `gen` and refresh token under that lease.

Disconnect-all must remove both legacy defaults and all new connector secrets, including present items whose metadata is missing. Search only the extension's exact schema namespaces and validated provider IDs, loading no values for enumeration. Its per-provider transaction marks absence only after both namespaces report no matching items. Per-connector removal must not invoke provider-wide delete. A cross-process removal or late refresh must not resurrect a deleted connector, credential or snapshot; use the existing epoch/revision fences and a durable deletion state for the target connector, with native concurrency tests.

## Runtime and presentation contracts

* Provider registry, client configuration and host allowlists use `providerId`.
* Runtime provider identity, normalized snapshot `id`, scheduler identity, cache key, account status, pause choice, revision target and preferences target use connector `id`.
* A runtime adapter sets both `provider.id` and every successful/error snapshot `id` to the connector ID. Merely renaming the provider object is insufficient.
* Presentation resolves the provider through validated connector metadata. Each card includes a distinguishable sanitized local label; trusted provider name remains visible. Fixed order is registry provider order followed by connector creation order, regardless of quota severity.
* Alerts track crossings/outages by connector ID. System notification templates use the fixed trusted provider name; local labels must not enter system notifications or tooltips under the existing text policy. A notification action resolves its exact connector target. Two same-provider notifications are separate entries, and the popup clarifies which connector is involved.
* `untracked-providers` may temporarily retain its key name but its documented semantics become connector IDs. New connector IDs must not be discarded by the indicator's current provider-only filter.
* The bar still shows at most the configured number of items, capped at five. A connector is an item; adding another account does not create additional provider capacity or merge balances.

## Restore defaults and deletion scopes

Offer **Restore default settings…** in General and a shortcut in Accounts. The confirmation explicitly states that theme, bar, popup, notifications and tracking return to defaults while saved connectors, credentials and OAuth client configuration remain. Reset in one dedicated delayed `Gio.Settings` batch, never delaying the shared instance. Under the redesigned contract this also clears paused connectors and makes the setup flow available again. Keep connector metadata, credentials/revision/status coordination, client IDs, per-provider terms acceptance, installed fonts and custom themes. A test classifies every schema key.

The development/demo source remains preserved in a synthetic session so restoring settings cannot accidentally switch the test window into real-network/keyring mode. Make this visible in the UI and test instructions. In production, “default settings” does not remove accounts. **Remove connector…** and **Disconnect all accounts…** are separately confirmed credential deletion actions; only the latter affects every account. Do not add an ambiguous “restore everything” action combining harmless appearance reset with destructive credential deletion.

Missing client IDs are not repaired by resetting appearance. The connector editor must explain the reason and provide the existing validated helper command and Check configuration again. Keyring failures have a separate recovery instruction. Do not accept an OAuth client secret into GSettings or replace malformed local configuration with a guessed client ID.

## Synthetic account mode

When the data source is demo, show a persistent notice: **Demo connectors use fictional data. No browser, keyring or provider request is used.** Inject simulated account controllers and connector storage into the same screens. Simulated Add, Rename, Connect, Pause, Remove and Restore must exercise the UI and update synthetic cards, including two connectors for the same provider. Simulated failures are explicit and selectable by the test harness. Real account controls are reached only by the user's explicit switch to live data; do not mix real credentials into demo state.

## Required validation

Pure tests cover collection bounds, supported providers, duplicate IDs, stable rename, migration preserving default identity and pause settings, empty initialized collection, reset classification and independent card selection. Controller tests cover two accounts of one provider, independent store/read/remove, closing a pending sign-in, one global sign-in owner, explicit consent, secret-free errors and held-refresh/delete races. Native libsecret tests use a disposable keyring to prove namespace separation, exact deletion, locked-item presence, disconnect-all coverage and partial-deletion recovery.

Native GTK tests create two same-provider connectors, rename one, simulate connection, pause/remove one and reopen Preferences to verify the other survives. Check focus movement, narrow width, translations, cancellation and actual settings values before/after Restore. Native Shell tests verify two distinguishable independent quota cards, bar selection, separate status/cache/alert keys, exact manage-account target, lifecycle teardown and zero late publication after removal. Demo tests assert zero production browser, keyring and HTTP calls.

Screenshots of Accounts with two Codex accounts, Add dialog, missing-client recovery, removal confirmation, empty state and restored settings are required for human validation. Record which screenshots are synthetic and which tests execute actual native processes. Real-provider sign-ins and Orca remain separate human tests unless explicitly exercised with suitable authorization and environment.

## Implementation handoff and measured evidence

The Accounts preferences implementation now follows the selected list/editor design, with real connector IDs, provider-scoped configuration, exact credential addressing, an explicit synthetic controller, Add/Rename/Track/Remove and both reset entry points. `lib/prefs/accounts.js` updates existing row state for account-status and pause changes rather than replacing focused rows. User labels render as plain text. Native Back and dialog cancellation detach editor subscriptions. A failed metadata write after confirmed credential removal reports a retry instead of claiming connector removal succeeded.

Controller regression tests first failed because two keys were collapsed into one, connector status was absent and removal returned no success/failure result. The new identity tests pass alongside the existing controller tests. Four isolated private-copy mutants were rejected: shared demo identity, API storage under provider ID, OAuth status under provider ID and an obsolete post-deletion gate assertion. A native `Gio.memory_settings_backend_new()` test confirms actual reset values for theme, scheme, bar, tracking and setup; it also verifies source/consent/username preservation and subsequent immediate setting edits. ESLint and scoped whitespace checks pass for the preferences implementation.

`tests/prefsConnectors.js` is the new native GTK scenario for Add, an independent second Codex connector, simulated connection, stable rename, cancelled and confirmed removal, actual reset values and configuration after reset. It must run in the root-owned private compositor before native UI success is claimed. The first full-suite integration run reported 470 passed and four failures outside the Accounts implementation: the connector core importing a provider-registry module across the core boundary, two obsolete first-use reset assertions in theme-effect tests, and Cyberpunk light framing contrast. These were reported to their respective owners; this snapshot is not the final integrated verdict.

### Independent review corrections

The first native GTK connector scenario passed four variants in the root-owned private compositor (`/tmp/gaq-connectors-native-output.txt`). A subsequent independent review found and corrected three gaps: the all-accounts row was incorrectly describing a completed scoped deletion as deleting every credential/cache; a failed exact deletion could not retry because its blocked provider rejected a new write ticket; and corrupted connector metadata had no recovery action. Scoped transaction copy now states the exact operation and points retries to the connector editor. Exact deletion bypasses write admission while retaining the backend's durable scoped-delete gate; OAuth token reading/revocation remains best effort and requires valid admission. A Cancel-default metadata-recovery dialog invokes the store's metadata-only reconstruction; demo reconstruction never touches live metadata. Corrupt metadata closes a stale editor and does not automatically open setup.

The two exact-retry tests first failed, then passed after correction while verifying sibling credentials remain. Scoped-versus-global presentation and recovery consent/failure tests pass. Four additional isolated mutants were killed (`/tmp/gaq-pref-review-mutants.json`). The integrated unit suite recorded **489 passed, zero failed** in `/tmp/gaq-account-review-fixes-full.log`. The native connector scenario now also tests corrupted metadata, cancelled reconstruction and successful demo reconstruction; this expanded scenario must be rerun by root before its native result is claimed.
